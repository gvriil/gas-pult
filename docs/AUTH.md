# Вход в панель

Как человек попадает в панель пульта, какие правила у каждого способа и что нужно владельцу, чтобы их включить.
Роль (владелец, участник, наблюдатель — `people.py`) проверяется на каждый запрос при любом способе входа: убрали
человека — любой его вход перестаёт работать сразу.

| Способ | Где | Включён |
|---|---|---|
| Mini App в Telegram | кнопка «📱 Панель» в боте | всегда: запрос подписан Telegram (`initData`) |
| «Войти через Telegram» | экран входа в браузере | всегда (`webauth.TgLogins`) |
| «Войти по коду — для владельца» | экран входа | всегда: код приходит владельцам в бот (`webauth.Auth`) |
| «Войти по почте» | экран входа | только если владелец настроил SMTP (`emailcode.py`) и человек привязал адрес |
| «Войти с Face ID / ключом» | экран входа | если настроен `[passkeys]` и стоит пакет (`passkeys.py`) |
| «Войти через Google» / «Войти через Яндекс ID» | экран входа | только если владелец зарегистрировал приложение и заполнил `[google]` / `[yandex]` (`oidc.py`) |

После входа из браузера — cookie-сессия на 30 дней (`HttpOnly`, `Secure`, `SameSite=Strict`); на сервере — только
SHA-256 от неё.

## Вход по коду на почту

**Как выглядит.** «Войти по почте» → адрес → письмо с 6 цифрами → ввести код → панель открыта. Ссылок для входа
в письме нет — только код.

**Кто может.** Только человек, который сам привязал адрес: «Настройки» → «Почта для входа и оповещений» → адрес →
код из письма. Адрес ложится в `people.json` (поле `email`; у владельцев — рядом, `emails.json`, 0600). Один адрес —
одному человеку. Новых людей вход по почте не заводит — для этого по-прежнему «Войти через Telegram».

**Правила** (перенесены из входа по почте другого проекта GASTECH):

- код — 6 цифр (`secrets.randbelow`), живёт **10 минут**, **5 попыток** — после пятого промаха код сгорает;
- на диске — только **HMAC-SHA256** кода (ключ `email_hmac` в `secrets.json` 0600 создаётся сам); адрес в файле
  кодов `email_codes.json` (0600, атомарная запись) тоже только HMAC; просроченное выбрасывается при каждом чтении;
- новый код на адрес — **не чаще раза в минуту и не больше 5 в час**; с одного IP — не больше 20 запросов в час;
  превышение — ответ `429` с `retry` (через сколько секунд можно);
- **одинаковый ответ** для привязанного и чужого адреса: «Если адрес привязан к пульту, мы отправили на него код».
  Письмо уходит в фоне — ответ не ждёт SMTP, время одинаковое. Для чужого адреса заводится «пустышка» с тем же
  счётчиком попыток: проверка кода отвечает так же, но войти нельзя. Лимиты у чужого адреса те же;
- письмо не ушло (SMTP недоступен) — код гасится, отправка не считается: можно сразу попросить снова;
- журнал — строки `auth: …` в `journalctl --user -u gas-pult-webapp`: запрос кода, вход, неудача, привязка,
  второй фактор. Без кодов; адрес — только как `i***@example.com`.

**Второй фактор.** В тех же настройках — «Код с почты после входа через Telegram» (по умолчанию выключено). Включено —
после подтверждения в Telegram панель просит ещё и код из письма; сессия выдаётся только после него. Если владелец
выключит почту на пульте (уберёт `[email]`), второй фактор перестаёт спрашиваться, иначе вход стал бы невозможен.
Запасной «код владельцу» второй фактор не спрашивает — он и так приходит только владельцу в Telegram.

**Оповещения.** «Оповещения на почту» — письмо, когда сессия встала на паузу по расходу (сейчас владельцам: пауза —
решение владельца). Функция для будущих событий — `emailcode.notify_email(service, uid, тема, текст)`: молча ничего не
делает, если у человека оповещения не включены или почта на пульте выключена.

### Что нужно владельцу: настроить SMTP

Без настроек вход по почте выключен: кнопки нет, API отвечает «выключено». Чтобы включить:

1. Создайте **пароль приложения** у поставщика почты (обычный пароль не подойдёт):
   - **Яндекс** (для РФ) — Яндекс ID → «Безопасность» → «Пароли приложений» → «Почта». Сервер `smtp.yandex.ru`,
     порт **465** (SSL). Логин — адрес ящика.
   - **Gmail** (для остальных) — нужна двухэтапная проверка; аккаунт Google → «Безопасность» → «Пароли
     приложений». Сервер `smtp.gmail.com`, порт **465** (SSL).
   - Другой поставщик — его SMTP-сервер с SSL на порту 465 (`host`, `port`).
2. Сохраните пароль на сервере пульта: `gas-pult email password` (ввод скрыт; ложится в
   `~/.config/gas-pult/secrets.json` с правами 0600). Можно и ключом `password` в `[email]`, но `config.toml`
   не 0600 — лучше `secrets.json`.
3. Добавьте в `~/.config/gas-pult/config.toml` (вне репозитория) секцию:

   ```toml
   [email]
   provider = "yandex"          # "yandex" (smtp.yandex.ru:465) | "gmail" (smtp.gmail.com:465) | "mailru"; или host/port
   user = "pult@example.com"    # логин SMTP — обычно сам адрес
   # from = "pult@example.com"  # адрес отправителя, если отличается от user
   # name = "gas-pult"          # имя отправителя в письмах
   # host = "smtp.example.com"  # свой сервер вместо provider
   # port = 465
   ```

4. Проверьте: `gas-pult email status`, затем `gas-pult email test ваш@адрес` — пробное письмо.
5. Перезапустите панель и бота: `systemctl --user restart gas-pult-webapp gas-pult`.
6. В панели: «Настройки» → «Почта для входа и оповещений» → привяжите свой адрес.

Письма уходят через `smtplib.SMTP_SSL` с `ssl.create_default_context()` (сертификат сервера проверяется), таймаут
20 секунд. Заголовки `From`, `To`, `Subject`, `Date`, `Message-ID` — через `email.message.EmailMessage`.

## Вход по ключу: Face ID, отпечаток, PIN (passkey)

**Как выглядит.** Один раз войти через Telegram → «Настройки» → «Ключи входа — Face ID» → «Добавить ключ этого
устройства» → подтвердить Face ID или отпечатком. Дальше на экране входа — «Войти с Face ID / ключом»: телефон сам
предложит ключ, адрес и коды не нужны. Ключей может быть несколько (телефон, ноутбук), у каждого — название и даты;
ненужный удаляется там же.

**В Telegram ключи не работают.** Во встроенном окне Telegram (особенно на iPhone) WebAuthn недоступен, поэтому в Mini
App кнопки нет, а в настройках — «Откройте панель в браузере». Добавлять ключ и входить по нему — из Safari, Chrome или
Edge по адресу панели.

**Правила** (перенесены из входа по ключу другого проекта GASTECH):

- ключ — discoverable (`residentKey: required`), личность проверяет устройство (`userVerification: required`),
  `attestation: none`;
- в устройство уходит случайный `user_handle` (32 байта) — не Telegram ID и не имя; один на человека для всех ключей;
  при входе он сверяется с владельцем ключа;
- вызов (challenge) хранится на сервере 5 минут и одноразовый: снимается при первой проверке; браузер знает только
  номер церемонии; у регистрации и входа — свои;
- начало регистрации или входа — не больше 20 раз за 10 минут с одного IP (`429`);
- `sign_count` сверяется: откат счётчика (клон ключа) — отказ;
- добавить и удалить ключ — только вошедшему, только свои ключи; убрали роль — вход по ключу перестаёт работать;
- если у человека включён второй фактор с почты — после ключа спрашивается и код из письма;
- журнал — строки `auth: passkey_…` (регистрация, вход, удаление, неудачи) без ключей и вызовов.

Хранение — `<data>/passkeys.json` (0600, атомарная запись): id ключа, открытый ключ, счётчик, `user_handle`, uid,
название, даты. Закрытый ключ остаётся в устройстве (и синхронизируется iCloud/Google, если так настроено у человека).

### Почему внешний пакет

Проверка ответа устройства — это разбор CBOR (attestationObject), ключей COSE и authenticatorData, проверка подписей
ECDSA/RSA/EdDSA, флагов и счётчика. Писать это самим рискованно: ошибка здесь — обход входа. Поэтому — **`webauthn`
2.8.0** (py_webauthn, Duo Labs, BSD-3-Clause, поддерживается). Это первая внешняя зависимость сервера, поэтому она
**необязательная**: `pip install "gas-pult[passkeys]"`, импорт ленивый. Без пакета ядро пульта работает как раньше,
вход по ключу просто выключен.

Пакет тянет за собой (проверено установкой 2.8.0 в чистое окружение, Python 3.14):

| Пакет | Версия | Лицензия |
|---|---|---|
| webauthn | 2.8.0 | BSD-3-Clause |
| cbor2 | 5.9.0 | MIT |
| cryptography | 50.0.2 | Apache-2.0 OR BSD-3-Clause |
| pyOpenSSL | 26.4.0 | Apache-2.0 |
| pyasn1 | 0.6.5 | BSD-2-Clause |
| pyasn1-modules | 0.4.2 | BSD |
| cffi | 2.1.1 | MIT-0 |
| pycparser | 3.12 | BSD-3-Clause |

В CI тесты ключей без пакета пропускаются (`pytest.importorskip`), а отдельная задача `passkeys` ставит `.[passkeys]`
и требует, чтобы ни один тест не был пропущен. Тесты собирают ответы устройства сами (ключ P-256, CBOR) — подписи
проверяет библиотека по-настоящему.

### API

| Метод | Кто | Что |
|---|---|---|
| `GET /api/login/methods` | без входа | поле `passkey` — включён ли вход по ключу |
| `POST /api/login/passkey/options` | без входа | `{id, options}` — номер церемонии и опции для `navigator.credentials.get` |
| `POST /api/login/passkey/verify` `{id, credential}` | без входа | cookie-сессия или `{state: "2fa", …}`; `503 code=off` — выключено |
| `GET /api/passkeys` | любой вошедший | `{enabled, keys: [{id, name, created, last_used}]}` — свои ключи |
| `POST /api/passkeys/options` | любой вошедший | опции для `navigator.credentials.create` |
| `POST /api/passkeys/add` `{id, credential, name}`, `/api/passkeys/remove` `{id}` | любой вошедший | добавить, удалить |

### Что нужно владельцу

1. Поставить пакет в окружение, где работает панель: `pip install "gas-pult[passkeys]"` (из репозитория —
   `pip install -e ".[passkeys]"` в том же venv).
2. В `~/.config/gas-pult/config.toml` (вне репозитория) — секция в конце файла:

   ```toml
   [passkeys]
   rp_id = "pult.example.com"                 # домен панели, без порта и схемы
   origin = "https://pult.example.com:8443"   # адрес панели в браузере целиком, с портом, если он не 443
   # rp_name = "gas-pult"                     # имя, которое покажет устройство
   ```

   `rp_id` должен совпадать с доменом в адресной строке (или быть его родителем), `origin` — с адресом панели точно,
   включая порт. Ключи привязаны к `rp_id`: сменили домен — ключи придётся добавить заново.
3. Перезапустить панель: `systemctl --user restart gas-pult-webapp`.

## Вход через Google и Яндекс ID

**Как выглядит.** На экране входа — «Войти через Google» или «Войти через Яндекс ID» → сайт Google или Яндекса →
выбрать аккаунт → панель открыта. Пароль от пульта не нужен, Telegram тоже.

**Кто может.** Только человек, у которого **уже есть роль** в пульте. Новых людей этот вход не заводит. Аккаунт
провайдера узнаётся одним из двух способов:

1. **Явная привязка** — человек вошёл (через Telegram, по почте или ключу) → «Настройки» → «Способы входа — Google,
   Яндекс ID» → «Привязать Google» → входит в свой аккаунт. Пульт запоминает номер аккаунта провайдера (`sub` у
   Google, `id` у Яндекса) → человек. Один аккаунт — одному человеку; у человека — по одному аккаунту каждого
   провайдера; отвязать — там же.
2. **Совпадение адреса** — без привязки, если адрес из аккаунта провайдера **подтверждён провайдером** и совпадает с
   почтой, которую человек уже подтвердил в пульте кодом («Почта для входа и оповещений», `people.by_email`):
   - **Google** — только при `email_verified: true` в проверенном `id_token`;
   - **Яндекс ID** — только если адрес — ящик на самом Яндексе (`@yandex.ru`, `@ya.ru`, `@yandex.com` и т. п.):
     такой адрес принадлежит аккаунту по построению. Признака «адрес подтверждён» API Яндекса не отдаёт
     (`login.yandex.ru/info` возвращает `default_email` без него), поэтому внешний адрес, указанный в Яндекс ID
     (например, `@gmail.com`), для входа по совпадению не годится — только явная привязка.

**Правила:**

- authorization code flow + **PKCE (S256)**; `state` — случайный, **одноразовый**, живёт **10 минут**, на сервере —
  только его SHA-256; к нему привязаны `code_verifier`, `nonce`, `redirect_uri` и cookie этого браузера `gp_oidc`
  (`HttpOnly`, `Secure`, `SameSite=Lax`, путь `/api/login/oidc/`): код обменяет только тот браузер, который начал
  вход (защита от подмены входа). `redirect_uri` при возврате сверяется с тем, что ушёл провайдеру;
- **права — только на вход**: Google — `openid email profile`, Яндекс — `login:email`. Ни Gmail, ни Drive, ни
  других данных: такие права требуют проверки приложения в Google, а пульту они не нужны. Токены провайдера не
  сохраняются — после проверки выбрасываются;
- **одинаковый ответ** для «нет такого человека», «адрес не подтверждён» и «у человека нет роли»: «Не получилось
  войти: этот аккаунт не привязан к пульту…» — адреса не перебрать;
- начало входа и привязки — **не больше 20 раз за 10 минут с одного IP** (`429`);
- ссылка на привязку из «Настроек» — одноразовая, **5 минут**;
- если у человека включён второй фактор с почты — после Google/Яндекса спрашивается и код из письма (номер ожидания
  передаётся во фрагменте адреса `/#2fa=…` — на сервер и в журналы прокси он не попадает);
- журнал — строки `auth: oidc_…` (начало, вход, неудача с причиной, привязка, отвязка) без кодов и токенов; адрес —
  только как `i***@example.com`.

Хранение — `<data>/oidc.json` (0600, атомарная запись), рядом с `emails.json`: привязки (провайдер и номер аккаунта →
человек, адрес маской, дата), ожидающие входы (SHA-256 `state`) и счётчики по IP (SHA-256 адреса).

**Внутри Telegram.** Google не пускает вход во встроенные окна (WebView), поэтому в Mini App кнопка открывает адрес
входа через `Telegram.WebApp.openLink` — в системном браузере телефона. Вход завершается **там**: панель откроется в
браузере, а не в Telegram (экран входа об этом предупреждает). Так же и привязка из «Настроек» в Mini App.

### Как проверяется id_token Google

Полностью, на стандартной библиотеке (`oidc.verify_id_token`), по OpenID Connect Core 3.1.3.7:

- заголовок: `alg` — строго `RS256` (`none`, `HS256` и прочее — отказ), ключ — по `kid` из JWKS Google
  (`https://www.googleapis.com/oauth2/v3/certs`, кэш на час; неизвестный `kid` — перечитать: Google меняет ключи);
- подпись **RSASSA-PKCS1-v1_5 / SHA-256** (RFC 8017, 8.2.2): `s^e mod n` → EM, который сравнивается целиком
  (`hmac.compare_digest`) с эталонным `00 01 FF… 00 || DigestInfo(SHA-256) || hash`. Ключи короче 2048 бит, `s ≥ n`
  и подпись не той длины — отказ. Сравнение всего блока, а не разбор, закрывает известные подделки подписи при
  `e = 3` (Bleichenbacher 2006);
- `iss` — `https://accounts.google.com` или `accounts.google.com`; `aud` — наш `client_id`; `azp` (если есть или
  `aud` — список) — наш `client_id`; `exp` не прошёл, `iat` не из будущего (допуск 2 минуты); `nonce` — тот, что
  ушёл в начале входа; `sub` есть.

Это сверх обязательного: токен и так получен напрямую с token endpoint Google по TLS с проверкой сертификата
(спецификация в этом случае разрешает не проверять подпись), но проверка подписи защищает и от ошибок в цепочке.

Яндекс ID — не OIDC: после обмена кода (с `code_verifier`) пульт спрашивает `https://login.yandex.ru/info` с
заголовком `Authorization: OAuth <токен>` и берёт `id` и `default_email`; `client_id` в ответе сверяется с нашим.

| `GET /api/oidc` | любой вошедший | `{google: {enabled, title, linked, email, at}, yandex: {…}}` — свои привязки |
| `POST /api/oidc/link` `{provider}` | любой вошедший | `{url}` — одноразовая ссылка на привязку (открыть в браузере) |
| `POST /api/oidc/unlink` `{provider}` | любой вошедший | отвязать |

### Что нужно владельцу

Без настроек вход выключен: кнопок нет, адреса входа отвечают «выключено». Адрес возврата (redirect URI) —
адрес панели снаружи **с портом**, если он не 443: `https://<адрес панели>/api/login/oidc/google/back` и
`…/yandex/back`. Пример ниже — `https://pult.example.com:8443`.

**Google** (Google Cloud Console, console.cloud.google.com):

1. Создайте проект (или выберите существующий) → «APIs & Services».
2. «OAuth consent screen» (в новой консоли — «Google Auth Platform» → «Branding» / «Audience»): тип **External**,
   название приложения, адрес поддержки. Права (scopes) — **только `openid`, `.../auth/userinfo.email`,
   `.../auth/userinfo.profile`** — ничего больше: с ними проверка приложения Google не нужна. Статус публикации —
   «In production» (в «Testing» входить смогут только адреса из списка тестировщиков, и вход живёт 7 дней).
3. «Credentials» («Clients») → «Create credentials» → «OAuth client ID» → тип **Web application**.
   «Authorized redirect URIs» — `https://pult.example.com:8443/api/login/oidc/google/back` (точно, с портом).
   «Authorized JavaScript origins» не нужны.
4. Скопируйте **Client ID** и **Client secret**.

**Яндекс ID** (oauth.yandex.ru):

1. «Создать приложение» → платформа **«Веб-сервисы»**.
2. Redirect URI — `https://pult.example.com:8443/api/login/oidc/yandex/back`; Suggest Hostname не нужен.
3. Доступы — **только «Доступ к адресу электронной почты» (`login:email`)**.
4. Скопируйте **ClientID** и **Client secret**.

**На сервере пульта:**

1. Секреты — командой, ввод скрыт (ложатся в `~/.config/gas-pult/secrets.json` с правами 0600):
   `gas-pult oidc secret google`, `gas-pult oidc secret yandex`. Можно и ключом `client_secret` в секции, но
   `config.toml` не 0600 — лучше `secrets.json`.
2. В `~/.config/gas-pult/config.toml` (вне репозитория) — секции в конце файла:

   ```toml
   [google]
   client_id = "….apps.googleusercontent.com"
   redirect_uri = "https://pult.example.com:8443/api/login/oidc/google/back"

   [yandex]
   client_id = "…"
   redirect_uri = "https://pult.example.com:8443/api/login/oidc/yandex/back"
   ```

   `redirect_uri` можно не писать, если панель запущена с `--url` — тогда он собирается из него. Он должен
   **в точности** совпадать с тем, что вписан у провайдера.
3. Проверьте: `gas-pult oidc status` (с `--url …`, если `redirect_uri` не задан) — оба «включён».
4. Перезапустите панель: `systemctl --user restart gas-pult-webapp`.
5. Проверьте вход: откройте панель в браузере → «Войти через Google». Не привязанный аккаунт с адресом, которого нет
   в пульте, должен получить «этот аккаунт не привязан к пульту». Свой — войти; в журнале
   (`journalctl --user -u gas-pult-webapp | grep oidc`) — `oidc_login_ok`.

**Выключить:** уберите секцию (или `client_id`) из `config.toml` и перезапустите панель; секрет — `gas-pult oidc
secret google` с пустым вводом. У провайдера можно удалить приложение или отозвать секрет. Привязки в `oidc.json`
остаются и снова заработают, если вход включить.
