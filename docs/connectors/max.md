# MAX — коннектор пульта

Код — `src/gas_pult/connectors/max_mcp.py`, тесты — `tests/test_max_mcp.py`, контракт — `docs/CONNECTORS.md`.
Источник — официальная схема OpenAPI MAX Bot API v0.0.34: https://github.com/max-messenger/api-schema (коммит
0016ff3) и https://dev.max.ru/docs-api — сверено 20.11.2026.

**Статус: каркас, не проверено на песочнице.** Песочницы у MAX нет, токена бота пока нет. Fixtures собраны по
схеме, данные выдуманные.

## Зачем

MAX — второй канал пульта рядом с Telegram: клиенты (жители УК, гости кафе, родители в фитнес-клубе) пишут боту
организации в MAX. Пульт видит входящие, готовит черновик ответа, человек нажимает «Да» — ответ уходит от бота.
Если Telegram станет недоступен, работа с клиентами не останавливается.

## Что умеет

| Инструмент | Что делает | Метод MAX Bot API |
|---|---|---|
| `max_list_messages` | Новые события бота: сообщения (новые, изменённые, удалённые), кто начал или остановил диалог; кто, когда, текст. Вложения — пометкой (`[фото] подпись`). Фильтры: `chat_id`, `only_incoming` | `GET /updates` без `marker` |
| `max_list_history` | История одного чата, новые первыми, до 100; листать — `before`/`after` (мс Unix) | `GET /messages?chat_id=` |
| `max_get_message` | Одно сообщение по `mid` | `GET /messages/{mid}` |
| `max_get_chat` | Чат: диалог, группа или канал; статус бота (активен, остановлен пользователем, удалён); с кем диалог | `GET /chats/{chatId}` |
| `max_get_bot` | Проверка ключа: имя и адрес бота, команды | `GET /me` |
| `max_propose_reply` | Черновик ответа в диалог или чат. Ничего не отправляет. Заранее проверяет, что бот в чате активен | `GET /chats/{chatId}` (чтение) |
| `max_apply` | Отправить подтверждённый черновик. Только при `GAS_MAX_WRITE=1` и подтверждении в пульте | `POST /messages?chat_id=` |

Токен идёт в заголовке `Authorization` как есть, без `Bearer` (так требует MAX; токен в адресе запроса MAX больше не
принимает). Коннектор вычищает токен из всех ответов и ошибок.

## Чего не умеет (и не будет без решения владельца)

- Не подтверждает очередь событий (`marker` не передаёт) и не отмечает сообщения прочитанными. По схеме MAX события
  считаются подтверждёнными, только когда передан `marker`.
- Не хранит переписку на диске. MAX предупреждает: Long Polling (`GET /updates`) ограничен по скорости и сроку
  хранения событий и «не подходит для production». Для постоянной работы нужен вебхук — отдельная служба пульта
  с HTTPS-адресом (HTTP-вебхуки MAX не принимает с 25.05.2026). Это следующий шаг, не этот PR.
- Если у бота включён вебхук — `GET /updates` событий не отдаст (по описанию метода; **не проверял**).
- Не скачивает файлы, фото и голосовые. Не отправляет вложения и кнопки.
- Не публикует в каналы, не редактирует и не удаляет сообщения, не меняет чаты и участников.
- Список всех чатов бота получить нельзя: `GET /chats` MAX отключил в июне 2026. Чаты видны по событиям.
- В группе бот видит сообщения, только если он администратор с правом `read_all_messages`.

## Ключ (делает владелец)

1. Нужен **верифицированный профиль организации, ИП или самозанятого — резидента РФ** на платформе «MAX для
   партнёров» (https://business.max.ru). Без него бота не создать (dev.max.ru → «Подготовка»).
2. business.max.ru → Чат-боты → создать бота → пройти модерацию (до модерации бот виден только создателю).
3. Чат-боты → ⋮ у бота → Настройки → скопировать токен.
4. Токен — в KeePassXC `gastech.kdbx`, группа `mcp/max`; на сервер — файлом `~/.config/gastech-mcp/max.token`
   (одна строка, права 0600). Путь меняется `GAS_MAX_KEY_FILE`. В чат токен не присылать.
5. Проверка: `max_get_bot` вернёт имя бота. Затем написать боту из своего MAX — `max_list_messages` покажет
   сообщение.

`GAS_MAX_BASE` меняет адрес API (тесты). Боевой адрес — https://platform-api2.max.ru (старый `platform-api.max.ru`
документация просит не использовать). По обзору dev.max.ru/docs-api нужно доверять сертификату Минцифры: если в
системе его нет, коннектор ответит «MAX недоступен: … CERTIFICATE_VERIFY_FAILED» — **не проверял**, проверить
первым вызовом с токеном.

## Лимиты

- 30 запросов в секунду на `platform-api2.max.ru`; коннектор держит не больше 25.
- Не больше 2 сообщений в секунду в один диалог или чат (ответы пульта идут по одному — с запасом).
- Текст сообщения — до 4000 символов.
- 429 — понятная ошибка «лимит запросов, подождите».

## Сценарий: модуль `uk-requests` (обращения жителей УК)

1. Житель пишет боту УК в MAX: «Нет горячей воды в кв. 12 с утра».
2. Утром (или по кнопке) пульт вызывает `max_list_messages` с `only_incoming`, модуль `uk-requests` заносит
   обращение в реестр, считает срок ответа (3 рабочих дня для жалобы на качество коммунальной услуги — п. 31
   Правил № 354, см. `templates/modules/uk-requests/CLAUDE.md`) и готовит ответ.
3. `max_propose_reply` → черновик в Telegram/панели пульта → диспетчер нажимает «Да» → `max_apply`. Ответ уходит
   тем же каналом, каким пришло обращение (п. 35 Правил № 416).

Оценка (**не замерено**, гипотеза для проверки на первом клиенте): разбор 20 обращений из мессенджера с внесением в
реестр и ответом — ~60 мин вручную → ~15 мин с пультом (чтение и черновики готовит пульт, человек проверяет и
нажимает «Да»). Замер — после токена и первой недели на реальном боте.
