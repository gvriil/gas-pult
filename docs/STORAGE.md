# Хранение служебных данных: JSON → SQLite

Решение владельца 22.11: служебные данные пульта переходят с файлов JSON на SQLite — малыми PR, с откатом.
Условия: перед переходом — копия JSON; на время перехода — запись в обе системы; вернуться к JSON — одним флагом;
замер до и после.

Код — `src/gas_pult/sqlstore.py`; подключение к общим `store.load` / `store.save` — `src/gas_pult/store.py`.

## Порядок модулей

| Шаг | Модуль | Файлы | Статус |
|---|---|---|---|
| 1 | люди | `people.json`, `terms.json`, `countries.json`, `prefs.json`, `emails.json`, `tours.json`, `ui.json` | готово (#431) |
| 2 | сессии браузера | `web_sessions.json` (`webauth.Auth`) | готово |
| 3 | фокус-ссылки | `focus.json` | готово |
| 4 | приглашения | `invites.json` | готово |
| 5 | задачи | `tasks.json` (список) | готово |
| 6 | события | журналы `*.jsonl` | дальше: дописываются строками, нужна своя таблица, а не «ключ-значение» |

Модуль переводится добавлением его файлов в `sqlstore.COLLECTIONS`. Остальные файлы при любом режиме живут в JSON —
в том числе рядом с сессиями `tg_logins.json` (ожидающие входы, живут 5 минут) и `web_confirm_tg.json` (запросы
подтверждения, 10 минут): короткоживущие, при откате терять нечего.

Режим общий для всех переведённых модулей. Отдельный флаг на модуль не нужен: копия, перенос, отметка «только в
SQLite» и выгрузка при откате работают по каждому файлу отдельно — откат одним флагом возвращает в JSON все модули сразу.

Файл-список (`tasks.json`) — через `sqlstore.LISTS`: строка на задачу по полю `id`; при чтении из SQLite порядок
восстанавливается по `created` (задачи добавляются в конец со временем добавления). ETag задач в режиме sqlite —
по данным, а не по файлу.

## Режимы

Ключ `storage` в `~/.config/gas-pult/config.toml` (переменная `GAS_PULT_STORAGE` важнее — для тестов и замера).
Службы видят смену режима без перезапуска: файл настроек перечитывается, когда меняется.

| Режим | Читаем | Пишем | Для чего |
|---|---|---|---|
| `json` (по умолчанию) | JSON | JSON | как было до перехода |
| `dual` | JSON (источник истины) | JSON, затем SQLite — под тем же замком | проверка перехода: `verify` должен быть чистым |
| `sqlite` | SQLite | только SQLite; JSON остаётся последней копией | после проверки dual |

Режим задаётся ключом `storage` в config.toml — командой `gas-pult storage enable dual|sqlite` (и `disable`), не
руками. На боевом сервере — `dual` с 22.11.2026 (копия JSON снята при включении); дальше — раздел «План перехода».

- **Ошибка SQLite в dual** запись не ломает: JSON записан, в журнале службы — `storage: … запись в SQLite не удалась`.
- **Расхождение в dual** (JSON поменяли мимо пульта или пульт работал в json): при следующей записи — предупреждение
  `storage: … расхождение` и SQLite выравнивается по JSON.
- **Замок** (`store.locked`, flock) — во всех режимах: он держит «прочитать → изменить → записать» целиком.
- **Тесты в другом режиме:** `GAS_PULT_TEST_STORAGE=dual|sqlite pytest …` — все тесты, кроме слоя JSON (`test_store.py`)
  и самого перехода (`test_sqlstore*.py`), идут в этом режиме; данные смотрят через фикстуру `stored` (conftest).

## Откат и защита от потерь

- Откат — `gas-pult storage disable` (или руками `storage = "json"`). В режиме sqlite каждая запись ставит рядом с
  JSON отметку `.<имя>.sqlite-only`; режим json или dual, увидев её, сначала выгружает SQLite в JSON. Поэтому откат
  одним флагом ничего не теряет, даже без команды.
- Обратно в sqlite после работы в json: JSON, изменённый мимо SQLite (подпись «время изменения:размер» не совпала с
  запомненной), переносится в SQLite заново.
- Копия JSON — `<данные>/backup/json-<дата>/` (папка 0700, файлы 0600): снимается автоматически один раз на
  коллекцию — при `storage enable` или при первом обращении к SQLite, если флаг поставили руками (в режиме dual — до
  первой записи). Какие коллекции уже в копии — `meta.backup_set`; копия первого PR считается копией модуля «люди».
  Перевели новый модуль — при первом включении снимается ещё одна копия, только с его файлами. Полная копия ещё
  раз — `gas-pult storage backup`.

## Устройство базы

- Файл `<данные>/pult.sqlite3`, права 0600 (и `-wal`, `-shm`).
- `journal_mode=WAL` — читатели не ждут писателя (бот и панель — разные процессы).
- `synchronous=FULL` — та же гарантия, что у JSON сейчас (`write_private` делает fsync): записанное переживает
  отключение питания. В WAL это один fsync на транзакцию; при нашей частоте записи цена — доли миллисекунды (замер ниже).
- `busy_timeout` — 10 с.
- Схема — по номеру `PRAGMA user_version`, шаги — список `SCHEMA`; новый шаг — добавлением в конец.
- Таблица `kv(collection, key, json, updated)`: коллекция — имя файла, ключ — ключ верхнего уровня (Telegram ID,
  отпечаток сессии, id задачи),
  значение — запись как в JSON. Почему не таблицы с колонками: файлы пульта — словари записей; такой вид повторяет их
  один в один — один код на все шесть модулей, сверка с JSON — построчно, откат — простая выгрузка, новое поле записи
  не требует миграции. Пишутся только изменённые строки. Колонки и индексы — потом, шагом схемы, когда понадобится
  запрос, а не чтение всего файла.
- **Одна запись — одна строка.** `store.get(файл, ключ)` в режиме sqlite читает одну строку `kv` по
  (collection, key); `People.role`, `tenant`, `terms`, `prefs` и другие чтения одного человека идут через неё. В json
  и dual — как `load(файл).get(ключ)`, без изменений.
- **Кэш коллекции** — в соединении (поток и процесс): строки `{ключ: json}`, их текст целиком (чтение — один
  `json.loads`, как у JSON-файла) и снимок записей (`marshal`). Кэш верен, пока не изменились `PRAGMA data_version`
  (коммит другого соединения) и `total_changes` своего; или пока длится тот же захват `store.locked` файла, под
  которым кэш проверен (коллекцию в это время никто другой не пишет). Откат транзакции кэш сбрасывает.
- **Запись** сравнивает запись со снимком: совпал — строка не сериализуется заново и не пишется. Снимок различает
  1, 1.0 и True — как текст JSON; разные байты при равных данных дают лишь лишнее сравнение, не пропуск изменения.
- **Замок базы при записи** — `flock` на `.pult.sqlite3.lock` (тот же, что у копии JSON). Процессы пишут разные
  коллекции в одну базу; без замка ожидание занятой базы — сон SQLite с шагом до 100 мс (busy handler), с замком —
  пробуждение сразу. Порядок замков — «файл коллекции → база». `synchronous=FULL` не менялся.
- `collections(name, version, json_sig, imported)` — версия схемы файла (как `.<имя>.v` у JSON) и подпись JSON на
  момент последней сверки; `meta` — где лежит последняя копия JSON (`backup`) и какие коллекции в копиях (`backup_set`).

## Команды

```
gas-pult storage status            # режим, база, строки по файлам, копия
gas-pult storage enable dual       # копия JSON (один раз) → перенос в SQLite → storage = "dual"
gas-pult storage verify            # JSON и SQLite: совпадают ли (для dual)
gas-pult storage enable sqlite     # после чистого verify в dual
gas-pult storage disable           # обратно в json: новое из SQLite → JSON, storage = "json"
gas-pult storage backup            # ещё одна копия JSON
```

`enable` и `disable` правят только строку `storage` в config.toml — комментарии и секции остаются.

## План перехода

1. **json → dual — сделано 22.11.2026.** `gas-pult storage enable dual`: копия JSON (`<данные>/backup/json-<дата>/`)
   снята, коллекции перенесены в SQLite. Чистый `storage verify` — первый пункт критерия шага 2.
2. **dual → sqlite — не раньше 23.11.2026 08:00 (сутки в dual). Решение — владелец.** Критерий — все три пункта:
   - `gas-pult storage verify` — по всем коллекциям нет расхождений (missing, extra, differ — пусто);
   - в журнале служб за сутки нет ни одной строки «запись в SQLite не удалась»:
     `journalctl --user -u gas-pult -u gas-pult-webapp --since "24 hours ago" | grep -c "запись в SQLite не удалась"`
     → `0` (заодно посмотреть все строки `storage:` — «расхождение» значит, что JSON писали мимо пульта);
   - `gas-pult storage status` — режим `dual`, строки по всем коллекциям.
3. **Перед включением** — свежая копия JSON: `gas-pult storage backup` (путь копии — в выводе).
4. **Включение** — `gas-pult storage enable sqlite`, **только после «да» владельца**. Службы видят смену без
   перезапуска.
5. **Проверка после:** `gas-pult storage status` → режим `sqlite`; в панели — вход, список окон, задачи, люди
   пространства; журнал служб — без новых строк `storage:` с ошибкой; через час — ещё раз.
6. **Откат** — `gas-pult storage disable`: всё новое из SQLite выгружается в JSON (`sqlstore.export_json` по каждой
   коллекции с отметкой `.<имя>.sqlite-only`), `storage = "json"`. Без команды тоже ничего не теряется: режим json
   или dual, увидев отметку, сам выгружает SQLite в JSON. Проверка после отката: `gas-pult storage status` → `json`,
   отметок `.*.sqlite-only` в папке данных нет, панель показывает те же задачи и людей; вернуться в dual —
   `gas-pult storage enable dual` (JSON снова источник истины).

### Замер 24.11: 100 клиентов, сервер отдельным процессом (`tools/bench-http.py`)

В `tools/bench-load.py` клиенты и сервер делили один процесс Python — время ответа завышалось. Новый замер: сервер —
отдельный процесс, режим json, 40 пространств, по 20 запросов на клиента (половина `/api/sessions`, четверть
`/api/history`, четверть — запись), прогрев не в замере. Время — мс.

| Клиенты | Текст JSON | Запросов/с | p50 | p95 | p99 | `/api/sessions` p95 | Ошибок |
|---|---|---|---|---|---|---|---|
| 16 | читается каждый раз | 75 | 185 | 283 | 1244 | 446 | 0 |
| 16 | кэш по подписи файла | 96 | 122 | 241 | 1222 | 425 | 0 |
| 100 | читается каждый раз | 21 | 638 | 3255 | 14915 | 3721 | 18 из 2000 |
| 100 | кэш по подписи файла | 18 | 234 | 2442 | 53941 | 3345 | 20 из 2000 |

Узкое место — **один процесс панели упирается в одно ядро** (сервер ~118 % CPU, клиент ~3 %): GIL, все запросы — в
одну очередь. Опрос стеков сервера раз в 5 мс (`GP_SAMPLE=<файл>`) под 100 клиентами: больше всего времени —
повторное чтение одних и тех же JSON-файлов на каждый запрос (`store.load_json`, `file_version`), ожидание
файлового замка (`store.locked`), обход пространств (`tenants.slugs`, `tenants.load` — метаданные всех пространств на
каждый `/api/sessions`). Хранение в SQLite этого не меняет (замер 22.11 выше: разница режимов — в пределах шума).

Сделано 24.11: текст JSON кэшируется по подписи файла (inode, mtime, размер; разбор — каждый раз, объект можно
менять) — при 16 клиентах +28 % запросов/с, p50 −34 %; очередь входящих соединений сервера — 128 вместо 5.

Цель для 100 клиентов: p95 < 500 мс, ошибок 0. Не достигнута. Что дальше (по убыванию отдачи):
1. Кэш списка пространств и их метаданных по подписи папки (`tenants.slugs`, `tenants.load`) — вызываются на каждый
   `/api/sessions`.
2. Готовый ответ `/api/sessions` на пул на 1–2 с (браузеры опрашивают раз в 3 с — одинаковый ответ десяткам людей).
3. Несколько процессов панели (`SO_REUSEPORT` или прокси на несколько портов): состояние панели в памяти (кэши,
   сессии браузера) — сначала вынести в хранилище; это шаг L.
Обрывы соединения («Connection reset by peer») при 100 клиентах — не разобраны: появляются и с очередью 128.
