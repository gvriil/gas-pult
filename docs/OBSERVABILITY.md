# Наблюдаемость: что падает и кто узнаёт

Разбор 22.11 (вопрос разбора архитектуры: «алерты на ошибки панели и бота — есть ли?»). Только факты: у каждой
строки — файл:строка в репозитории или команда проверки. Ссылки на код — по `main` на 22.11 (коммит `3b27aae`).
«Не проверял» — так и написано.

## Коротко

- **Пульт сам о своих сбоях почти не сообщает.** Ошибки панели и бота уходят только в журнал службы (`journalctl`)
  и в журнал событий чата. Автоматически их никто не читает.
- **Сообщает владельцу** (Telegram, а также телефон и почта — что он выбрал, `bot.py:339` `broadcast`): лимит
  подписки у окна, ошибка API поставщика и переключение модели, сообщение не отправлено в окно, автотест
  поставщиков не прошёл, срочное в брифинге, красный CI **у открытых PR**.
- **Внешние сторожа сервера** (вне репозитория, `~/.local/bin`): `ram-watch` (мало памяти) и `infra-watch` (другие
  сервисы, **не пульт**). Доставка — `gas-notify`: Telegram напрямую через API бота, плюс tmux, рабочий стол и
  очередь `~/.local/state/gas-alerts/queue.jsonl`, которую хук показывает каждой сессии Claude.
- За 7 дней в очереди сторожей нет **ни одного** сообщения о пульте (типы записей: расход, перезагрузка ВМ,
  усыпление окон, ночные отчёты).

## Чем ещё мешает журнал

- Журнал служб пульта за сутки 22.11: около 38 тыс. строк `sudo` (tmux пространств вызывается через `sudo`) против
  ~1,5 тыс. строк самого пульта. Трассировки тонут в этом шуме.
- `menu: …: setChatMenuButton: Bad Request: user not found` — 118 строк за сутки (кнопка меню человеку, которого
  Telegram не знает). Не сбой, но шум.
- `BrokenPipeError` — 15 за сутки: человек ушёл, не дождавшись ответа. Не ошибка.
- `journalctl -p warning` ничего не находит: пульт пишет ошибки через `print` без уровня важности.

## Предложения (малые, по пробелам)

1. **Событие и оповещение при 5xx панели** — ~40 строк и тест, 1–2 ч. В `dispatch` (`webapp.py:6144`) — последний
   `except Exception`: ответ 500 JSON `{"error": "внутренняя ошибка", "id": …}`, трассировка в журнал, событие
   `server_error` (путь, тип исключения, без тела запроса) в `chat-events.jsonl`. Бот в цикле `monitor` читает новые
   `server_error` и `js_error` и шлёт владельцу одну строку `broadcast(kind="error")` — не чаще раза в 30 минут, с
   числом событий за окно. Человек вместо обрыва видит понятную ошибку.
2. **`OnFailure=` у трёх служб** — ~15 минут, на сервере (вне репо) и в образце `cli.py:175`. Шаблон
   `gas-pult-failed@.service` вызывает `gas-notify "служба %i упала"`. `gas-notify` шлёт через API Telegram напрямую,
   поэтому работает и когда процесс бота лежит. Плюс `StartLimitBurst=5`, `StartLimitIntervalSec=300`, чтобы падение в
   цикле стало видимым состоянием `failed`.
3. **Сторож `main` CI** — ~30 строк, 1 ч. В утренний брифинг добавить строку «`main` красный с …» (`gh run list -b main
   -w CI -e push -L 1`), а вне утра — один раз через 1 ч красного. Альтернатива дороже по минутам GitHub: macOS и
   на PR, когда меняются `tests/` или `src/`.
4. **Признак жизни бота и панели** — ~20 строк, 30 минут. Бот раз в минуту обновляет файл-отметку в папке данных
   (из цикла `monitor`); `infra-watch` (вне репо) проверяет: отметка свежее 3 минут и панель отвечает локально
   (`curl --resolve … 127.0.0.1`). Два сбоя подряд → `gas-notify` — как у остальных его проверок.
5. **Диск и журнал Caddy** — ~10 строк, 15 минут, вне репо. В `ram-watch` — порог диска 85 %. В Caddyfile —
   `roll_keep 14` (или ротация по дням), чтобы утром был виден журнал ночи.

Порядок по пользе: 2 → 1 → 3 → 4 → 5. Пункты 1 и 3 — код пульта (отдельный PR каждый), 2, 4, 5 — настройка сервера.
