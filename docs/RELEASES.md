# Два канала выпуска — план

Задача 46, решение владельца от 07.11.2026: пульт владельца идёт за `main`, как сейчас; пространства клиентов —
стабильные теги раз в неделю. **Это только план.** Ничего не переключено: теги не ставятся, `/srv/pult/release` не
создаётся, службы и юниты не меняются. Каждый этап (раздел 9) — отдельное «да» владельца.

Код — `main` на `02f6e6b` (#122). Метки треков — `docs/metrics/audit-2026-11.md`, раздел 10.

## 1. Как сейчас

**Пульт владельца.** Два процесса — бот (`gas-pult run`) и панель (`gas-pult webapp`) — пользовательские службы
владельца (`systemctl --user`). Код — живая копия репозитория на ветке `main`: `PYTHONPATH=<копия>/src` в юнитах
(у бота — отдельным drop-in: `gas-pult service install` его не пишет). Выкладка — `git pull` в живой копии и
`systemctl --user restart gas-pult gas-pult-webapp`. Каталог данных общий для обоих процессов (`GAS_PULT_DATA_DIR`,
по умолчанию `~/.local/share/gas-pult`).

**Пространства.** Свой код пульта они сейчас **не запускают**. Служба пространства `pult_t_<slug>.service`
(`tenant_admin.service_unit`, `tenant_admin.py:183`) — только сервер tmux от пользователя пространства в песочнице;
`pult-share-<slug>.timer` — только `find … chmod g+r`. Код пульта доходит до пространства тремя путями:

| Путь | Чей код | Когда обновляется |
|---|---|---|
| Панель и бот обслуживают тестировщиков и гостей: окна через `sudo -u … tmux -S …` (`tenants.tmux_of`), команда запуска Claude (`tenants.command`), оболочка в окне пространства (`space_sessions.sh`, буфер tmux в `space_files`) | живая копия, `main` | при каждой выкладке пульта |
| Файлы, которые `pult-tenant create` и `pult-tenant agents` раскладывают в пространство от root: `tenant.json`, `budget.json`, профили и `secrets.json`, слепые проверяющие и их сторож (`config/claude/agents`, `config/claude/hooks`); в задаче 44 (ещё не на `main`) — хук скрытия секретов `hooks/gas-pult-secrets.py` и записи в `config/claude/settings.json` | та копия, откуда владелец запустил `sudo bin/pult-tenant` (скрипт берёт `src` рядом с собой: `bin/pult-tenant`, `sys.path` от `realpath(__file__)`) | когда владелец сам запустит `create` или `agents` |
| Claude Code пространства — своя установка в `home/.local` пространства | не наш код | вручную (`docs/TENANTS.md`, шаг 4) |

**Вывод.** «Сервис пространства запускает `current`» в буквальном виде сегодня некому: процесса пульта у
пространства нет. Канал «пространства» поэтому делится на две части:
- **то, что лежит в пространстве и исполняется там** — хуки, агенты, сторож, раскладка папок и файлов `pult-tenant`;
  это переводится на тег почти бесплатно (этапы 2–3);
- **то, что клиент видит в браузере** — панель. Чтобы клиент видел версию тега, нужна **вторая панель** —
  отдельный процесс из `current` только для пространств (этап 4). Без неё клиенты видят интерфейс `main`, а тег
  управляет только тем, что внутри пространства.

## 3. Теги

**Имя:** `spaces-<год>-W<неделя ISO>` — `spaces-2026-W46`. Срочное исправление на той же неделе —
`spaces-2026-W46.1`, `.2`. Тег аннотированный; в сообщении — список PR между прошлым и этим тегом.

Не `v*`: на `v*` срабатывает `.github/workflows/release.yml` — он сам создаёт публичный GitHub Release. Пакетные
версии (`v0.2.0`, `__version__`) остаются отдельной историей.

**Кандидат** — последний коммит `main`, которому не меньше 7 дней:
`git rev-list -1 --before="7 days ago" origin/main`.

**Критерии** (все — иначе неделя пропускается, в пространствах остаётся прошлый тег):
1. **CI зелёный на этом коммите** — полная матрица `main` (Ubuntu и macOS, Python 3.11–3.14, `passkeys`, `build`),
   а не только проверка PR.
2. **Неделя в `main` без отката:** между кандидатом и сегодняшним `main` нет коммита `Revert …` и PR `fix/*`, который
   чинит что-то из PR кандидата (связь — по номеру PR в описании исправления). Есть — кандидатом становится коммит до
   сломанного PR, и проверка повторяется.
3. **Ручная проверка демо** на копии тега: `?demo` и `?demo&home&spaces=1` — ширина 390 и 1366, светлая и тёмная тема,
   консоль без ошибок; простой режим тестировщика; «Файлы сессии»; лист «Расход» с запасом.
4. **Проверка пространства** после переключения (этап 3 и дальше): `sudo …/current/bin/pult-tenant check A B` в обе
   стороны, `gas-pult doctor`, одна сессия в демо-пространстве: создать → сообщение → файл → закрыть → продолжить.
   Не прошло — откат (раздел 7) в тот же час.

**Кто и когда.** Понедельник, утро. Агент (сессия Claude Code в живой копии) готовит кандидата: проверяет критерии
1–2, собирает список PR и черновик раздела CHANGELOG, прогоняет демо (критерий 3) и присылает владельцу итог.
Владелец отвечает «да» — агент ставит и отправляет тег (`git tag -a` и `git push origin <тег>` — внешнее
действие, только после «да»). Копию и переключение делает владелец через `sudo` (раздел 8).

## 4. Копия кода и ссылка `current`

```
/srv/pult/release/                 root:root 0755
├── spaces-2026-W45/               root:root, папки 0755, файлы 0644 (скрипты bin/ — 0755); только чтение
├── spaces-2026-W46/
│   └── RELEASE                    тег, коммит, дата, кто поставил, sha256 дерева
├── current -> spaces-2026-W46     символическая ссылка
└── log.jsonl                      журнал: prepare / use / rollback — кто, когда, с какого тега на какой
```

- **Архив, не `git worktree`.** `git archive <тег> | tar -x` из живой копии: без `.git`, без связи с домашней папкой
  владельца (рабочая копия worktree хранит путь к `.git` в `/home`, а пространства `/home` не видят — `ProtectHome`).
  Распаковка — во временную папку `<тег>.tmp`, проверка (`python3 -I -c "import gas_pult"` с `PYTHONPATH`,
  `python3 -m compileall -q`), затем переименование в `<тег>`. Готовая папка не меняется никогда; новый выпуск —
  новая папка.
- **Права.** Всё — root, запись только root. Пространства видят `/srv/pult/release` на чтение (`ProtectSystem=strict`
  делает `/srv` только для чтения, но не прячет) — это открытый код репозитория, секретов в копии нет и быть не
  должно (проверка в `prepare`: нет `config.toml`, `token`, `secrets.json`, `.env*`).
- **Ссылка `current`** переключается атомарно: новая ссылка рядом и `mv -T` поверх старой. Половинного состояния нет.
- **Хранится** четыре последних выпуска; старше — удаляются только командой владельца (`--yes`), не сами.
- **`bin/pult-tenant` из копии работает без правок:** путь к `src` он считает от `realpath(__file__)`, поэтому
  `sudo /srv/pult/release/current/bin/pult-tenant …` берёт код именно этого тега.

## 5. Совместимость: пульт владельца новее пространств

`main` всегда впереди тега на неделю и больше. Что может сломаться и правило на каждый случай:

### 5.1. Файлы пространства (`/srv/pult/tenants/<slug>/`)

Пишет их `pult-tenant` (канал пространств, от root), читает панель (`main`): `tenant.json`, `budget.json`,
`audit.jsonl`, профили, раскладка папок `tenants.paths`.

- **Кто пишет файл — тот в одном канале.** Файлы пространства пишет только `pult-tenant` из `current`. Панель
  `main` их только читает.
- **Панель читает все прошлые формы.** Так уже сделано для `budget.json` (старый `{"daily_usd": 3}` читается). Новое
  поле в файле пространства появляется сначала в `pult-tenant` и попадает в пространства с тегом; панель `main` до
  этого должна работать без него (значение по умолчанию).
- **Новая папка или путь** в `tenants.paths` — панель проверяет, есть ли они, а не предполагает. Пример: корзина
  `trash/sessions` у старого пространства может отсутствовать.

### 5.2. Хуки Claude Code в пространстве

Сторож слепой проверки (`templates/agents/slepaya_proverka_storozh.py`), агенты (`reviewers.py`), в задаче 44 —
хук скрытия секретов и его записи в `settings.json`.

- **Хук самодостаточен:** только стандартная библиотека, ни одного импорта из `gas_pult`, системный `python3`. Так он
  не зависит от того, какая версия пульта рядом.
- **Хук зависит от версии Claude Code пространства,** а не пульта: формат ответа хука (`updatedToolOutput`,
  `suppressOriginalPrompt`) меняется вместе с Claude Code. В `RELEASE` и в критерий 4 входит версия Claude Code каждого
  пространства (`claude --version` от пользователя пространства).
- **Правила, продублированные в панели** (в задаче 44 — копия `RULES` в `index.html` для проверки поля ввода), у
  панели `main` и хука из тега могут разойтись. Это безопасно, пока расхождение только в сторону строгости: панель
  проверяет до отправки, хук — после, срабатывает тот, кто строже. Ослабить правило можно только в обоих каналах
  одновременно — то есть с тегом.
- **Записи в `settings.json`** ищутся по метке (`TAG`) и при раскладке **заменяются целиком**: и новая версия, и
  откат на старую должны убирать свои прежние записи, а не только добавлять. Проверить тестом до этапа 3.
- **Список агентов в панели** (`reviewers.public()`, `main`) может назвать агента, которого в пространстве ещё нет.
  Экран модуля для пространства должен показывать то, что лежит в его `config/claude/agents`, а не список пакета.

### 5.3. Панель ↔ пространство

Сегодня это не HTTP API, а команды: `sudo -u … tmux -S <сокет> …`, строка запуска Claude из `tenants.command`,
скрипты оболочки `space_sessions.sh` в окне пространства, журналы в `config/claude/projects` (чтение через
`pult-ro`). Всё это исполняется кодом `main` против раскладки, созданной тегом.

- Новая команда или скрипт панели не должны требовать того, чего в пространстве ещё нет (нового файла, новой
  папки, новой программы в `PATH` пространства). Нужно новое — сначала в тег через `pult-tenant`, через неделю —
  в панель.
- Тест: `tests/test_tenant_testers.py` (настоящие серверы tmux) — запускать против раскладки прошлого тега
  (раздел 10, CI).

### 5.4. Каталог данных пульта — при второй панели (этап 4)

Пока панель одна, вопроса нет. Со второй панелью две версии кода пишут одни файлы: `people.json`, `invites.json`,
`web_sessions.json`, `tg_logins.json`, `focus.json`, `space-drafts.json`, `space-budget/<slug>.json`, `prefs.json`,
`ui.json`, `tours.json`, `terms.json`, `countries.json`.

- **Сейчас запись защищена только внутри процесса** (`threading.Lock`, `people.py:90`): два процесса потеряют
  изменения друг друга. До этапа 4 — межпроцессная блокировка (`fcntl.flock`, стандартная библиотека) на каждый
  общий файл, как уже сделано для окон (`locks/`).
- **Старая версия не должна терять новые поля.** Сейчас теряет: `people.add` собирает запись заново из известного
  списка ключей (`people.py:139`–`143`) — поле, которое добавит `main`, панель тега при смене роли выбросит.
  Правило: при перезаписи записи — сохранять все неизвестные поля (`{**old, …}`); тест на каждый общий файл:
  «запись с лишним полем → любая операция → поле на месте».
- **Разделить владение.** Сессии входа, черновики и настройки тестировщиков — каталог данных второй панели
  (`GAS_PULT_DATA_DIR`), общими остаются только `people.json`, `invites.json`, `tg_logins.json` (их пишет и бот
  владельца) и `space-budget/` (пополняет владелец). Чем меньше общих файлов, тем меньше правил.

## 6. Миграции

- **В `main` миграции только добавлением:** новое поле с умолчанием, старая форма читается. Удалить или
  переименовать поле — в два шага: сначала тег, который умеет без поля, потом `main`, который перестаёт его писать.
- **Каталог данных** мигрирует сам при старте процесса, с копией прежнего файла рядом (`<файл>.bak-<время>`) — как
  `owner_space_fix` в `webapp.py`. Только вперёд и только добавлением, чтобы прошлый тег читал результат.
- **Файлы пространства** мигрирует `pult-tenant` при раскладке нового тега (раздел 8, `release use`): от root,
  с бэкапом изменённого файла в `/srv/pult/etc-backup/` (так уже делается для `fstab` и `settings.json`).
  Миграция, которую нельзя откатить заменой ссылки, в недельный тег не входит — только отдельным выпуском с планом
  отката и «да» владельца.

## 7. Откат

- **Пространства:** `current` → прошлый тег (`release use <прошлый тег>` или `release rollback`), затем раскладка
  хуков и агентов прошлого тега во все пространства (та же команда). Работающие окна не перезапускаются: хук
  подхватывается на следующем вызове, агенты — на следующем запуске. При второй панели — ещё
  `systemctl --user restart` её службы.
- **Пульт владельца:** как сейчас — `git revert` в `main` через PR (или `git checkout <коммит>` в живой копии на время)
  и перезапуск двух служб.
- **Сам план** (этапы 1–5) откатывается по шагам в разделе 9; ни один этап не трогает службы tmux пространств.

## 8. Что меняется в `pult-tenant` — только описание

Новая команда `pult-tenant release` (не реализуется в этой задаче):

| Подкоманда | Что делает | Откат |
|---|---|---|
| `release prepare <тег>` | проверить: тег есть, аннотирован, лежит на `origin/main`, не моложе 7 дней (или `--hotfix`); `git archive` из живой копии во `release/<тег>.tmp`; проверка импорта и `compileall`; нет файлов с секретами; файл `RELEASE`; переименование в `release/<тег>`; запись в `log.jsonl` | `rm -r /srv/pult/release/<тег>` (пока на него не указывает `current`) |
| `release use <тег>` | переключить `current` атомарно; раскладка из нового `current` во все пространства — агенты, сторож, хуки (`agents` и в задаче 44 — `guard`), с бэкапом изменённых файлов; миграции файлов пространства; `log.jsonl` | `release use <прошлый тег>` |
| `release rollback` | `use` прошлого тега из `log.jsonl` | `release use <тег>` |
| `release list` | выпуски, на что указывает `current`, версия Claude Code в каждом пространстве | — |
| `release prune --keep 4 --yes` | удалить старые выпуски, кроме `current` и прошлого | нет — только по «да» |

Все подкоманды — с `--dry-run`, как остальные команды `pult-tenant`. Запуск — `sudo bin/pult-tenant release …` из
живой копии (так тег можно подготовить, когда `current` ещё нет), дальше — из `current`.

## 10. CI

- **Новый workflow на теги `spaces-*`** (не `v*`): ruff, полная матрица pytest и `build`, как на `main`; плюс
  проверки тега — коммит лежит на `main`, ему не меньше 7 дней (кроме `.N`), прогон CI на этом коммите в `main` был
  зелёным (`gh api` по `check-runs`). Красное — тег не используется (`release prepare` проверяет то же сам и
  откажет).
- **Совместимость с прошлым тегом:** в CI `main` — задание, которое берёт последний тег `spaces-*`, раскладывает
  пространство его `tenant_admin` во временную папку (как тесты `tenant_admin` в `tests/test_tenants.py`, без
  `sudo`) и прогоняет тесты панели `main` против этой раскладки (`test_tenant_testers`, `test_space_budget`).
- GitHub Release на недельные теги **не создаётся** (публикация — внешнее действие; решение владельца).

## 11. CHANGELOG и «Что нового»

- В `CHANGELOG.md` раздел `[Не выпущено]` остаётся для `main`. При теге — PR «Выпуск `spaces-2026-W46`»: пункты PR,
  вошедших в тег, переезжают в раздел `## [spaces-2026-W46] — <дата>`; более новые остаются в `[Не выпущено]`.
- Чтобы перенос был механическим, каждый пункт CHANGELOG заканчивается номером PR `(#N)` и начинается с метки трека,
  если она не `[общее]`. Список PR тега — `git log <прошлый тег>..<тег> --oneline` (номера в заголовках слияний).
- `whatsnew.json` у второй панели — её собственная копия из тега: клиент видит «Что нового» ровно своей версии без
  отдельной разметки. Пока панель одна, тестировщики видят `whatsnew.json` из `main`.
- В «Что нового» и в «Настройки» второй панели — строка версии из `RELEASE` (новое поле `/api/meta` — добавлением).

## 12. Что требует `sudo` владельца

- Этап 2 и каждая неделя: `sudo bin/pult-tenant release prepare <тег>` — запись в `/srv/pult/release` (root).
- Этап 3 и каждая неделя: `sudo /srv/pult/release/current/bin/pult-tenant release use <тег>` — ссылка и раскладка в
  пространства (root пишет в `config/claude/hooks` пространств).
- Откат: `sudo …/pult-tenant release rollback`.
- Не нужен `sudo`: тег, CI, CHANGELOG; служба второй панели и Caddy (пользовательские), её перезапуск.
- Вне сервера: запись DNS для адреса второй панели (этап 4) — владелец; правила проброса портов гипервизора не
  меняются, если вторая панель живёт на том же внешнем порту под другим именем.

## 13. Открытые вопросы владельцу

1. **Вторая панель (этап 4)** — сейчас или когда появится первый клиент? Без неё канал пространств управляет только
   тем, что исполняется внутри пространства, а интерфейс клиенты видят из `main`. Предложение: этапы 0–3 сейчас, 4 —
   с первым клиентом.
2. **Публиковать ли недельные теги** как GitHub Releases (публичные страницы с архивом) — или только тег?
3. **Внеочередной тег** для исправления безопасности: можно ли без недели в `main` (CI зелёный, сутки в `main`,
   критерии 3–4)? Предложение — да, суффикс `.N`.
4. **День и время** недельного тега и кто нажимает «да» — только владелец или и участник с ролью?
5. **Хуки — копией или ссылкой.** Копия в пространство (как сейчас) требует раскладки при каждом переключении; ссылка
   хука на `/srv/pult/release/current/…` переключается вместе с `current` мгновенно, но сторож перестаёт быть файлом
   внутри пространства. Предложение — копия (проверено), ссылка — после отдельной проверки в песочнице службы.
6. **Сколько хранить выпусков** — предложено четыре.
